## 2026-09-10：Milestone 3 —— Q&A 知识蒸馏 + LangChain RAG 问答

- 范围：`server/`（蒸馏 / 审核 / 向量化 / 检索加权 / RAG 问答）、`client/`（问答面板、引用卡、录入表单、蒸馏按钮）。
- 知识原子从 markdown 切片改为标准「问题 + 答案」：`question` + `answer` + 六维拆解
  （`technique` 表现手法 / `persona` IP 人设 / `hook` 开头钩子 / `structure` 结构节奏 /
  `transfer` 迁移建议 / `transfer_risk` 失败风险）+ `evidence` + 溯源，回答「为什么这个内容结合这种演绎能爆」「换别的方式能不能爆」。

### 架构决策（两条已拍板）

- **LangChain 仅作编排层**：`langchain_core` 的 import 只允许出现在 `app/services/lc.py`；
  既有 chunking / DashScope embedding / SQLite JSON 向量 / Python 余弦检索全部不动，
  由 `KbRetriever` 适配器桥接，**零数据迁移**。链 = `RunnableLambda(_retrieve) | _prompt | _model | _guard`。
  装不上时自动退化为等价 shim（`/health` 显示 `lc:"fallback"`），两条后端跑同一份链代码。
- **Q&A 来源双通道**：`AI 蒸馏`（作品分析 → 草稿 → 人工审核）与 `手动录入`（人写即终态，**不调用模型，无 key 也能用**）。

### 数据与语义

- `kb_documents` 新增 `doc_type`（`general` | `qa`，走 `_COLUMN_MIGRATIONS`）；新表 `kb_qa_pairs`（`schema.sql`）。
  `kb_chunks` **不加列**：`qa_id` / `question` / `kind='qa'` 全进既有 `meta` JSON，零 DDL 风险。
- Q&A 路径刻意**绕过 `chunk_text` 的 500 字符切分**，每对一 chunk（整块封顶 1500 字符，只截尾部的迁移/风险段，Q+A 永不拆散）。
- 两阶段沿用：`蒸馏/录入 → doc(pending) + pairs(draft) → 人工 approve → vectorize（只嵌 approved）→ ready`。
  **未审核内容永不进入 `kb_chunks`**。同 `(source_type, source_id)` 幂等复用；`force=true` 重蒸馏**只删草稿**，`approved` 永不自动删除。
- 检索兼容：Q&A chunk 与旧 markdown chunk 同表同 `embedding` 列，`search()` 自动覆盖两类，`KbSearchHit` 字段集不变。
  `qa_boost` 默认 `0.0`（关闭），关闭时排序与切片对既有输出**逐字节相同**；`score` 保持原始余弦，另给 `rank_score`。
- **RAG 拒答三闸**：① 检索为空 → 不调模型直接拒答；② `top_score < DATAPP_RAG_MIN_SCORE`（默认 0.25）→ 不调模型拒答并回传 `top_score`/`retrieval_count` 供校准；
  ③ 模型 `citations` 与本次检索命中集求交为空 → **强制拒答，原始答案文本丢弃不展示**。引用 `quote` 经空白归一做子串校验 → `verified`。
- 防幻觉：`sanitize_qa_payload` 用服务端登记来源表给 `evidence.ref` 求交，越界引用丢弃并计数，未知维度收进 `extra`，单对脏数据不拖垮整批，**0 对存活直接抛错不落空文档**。
- `lc.py` **直接赋值**（非 `setdefault`）把 `LANGCHAIN_TRACING_V2` / `LANGSMITH_TRACING` / `LANGCHAIN_TRACING` 写死为 `false`，防 prompt 与采集内容外发；`/health` 回显 `lc_tracing:false`。

## 2026-09-10：看板交互重做 —— 结果内嵌 + 查看/重做拆分 + 下一步引导

针对三处体验问题：① 已分析过的内容只有一个语义漂移的「重新分析」按钮，已审核内容重复审核直接 409；
② 结果面板渲染在内容列表**最底部**，与触发它的卡片脱节；③ 出结果后没有任何「下一步能干什么」的提示。

### 1. 卡片动作拆成「查看 / 重做」成对

每条内容的三类动作从「一个按钮语义漂移」改为稳定成对：已产出过就给 `查看 X` + `重做 ↻`，
没产出过才给一次性的 `分析` / `自动审核` / `单篇报告`，彻底消掉 409 这条错误路径。

| 动作 | 未产出过 | 已产出过 |
|---|---|---|
| 分析 | `分析` | `查看分析` + `重析 ↻` |
| 审核 | `自动审核` | `查看审核` + `重审 ↻` |
| 报告 | `单篇报告` | `查看报告` + `重报 ↻` |

### 2. 重新分析可注入补充视角（主体方向不动）

`POST /contents/{id}/analyze` 新增可选 body `{focus}`（≤500 字；**body 可整段省略**，旧调用行为不变）。

**红线守住的写法**：`focus` 只拼进 **user** 侧，system 侧只追加一句限定作用域的约束
（「不得改变 verdict 判定口径、不得改变输出 JSON 结构、不得引入给定数据之外的事实或数字」），
既有的 `_SYSTEM_JSON` 分析框架、防幻觉铁律、`sanitize_analysis_payload` 白名单求交**一字未改**。

- 落库：`analyses` 加 `focus` 列（走 `_COLUMN_MIGRATIONS`，幂等），同时写进 `payload.focus`；Markdown 在「判定」之前渲染
  `## 补充关注点（用户指定）` 段并注明不改变口径 —— 让「这一次是非标准分析」在审计时一眼可见。
- **重新分析 = 新增一条记录**，旧分析保留可回看（`test_two_analyses_keep_history` 锁定）。

### 3. 重新审核 force（同事务覆盖，失败不清空）

`POST /contents/{id}/review?force=true`。`save_review_batch(..., replace=True)` 在**同一事务内**
按 FK 逆序清掉旧 `evidence → review_decisions → claims` 再写新批次。
关键点：删除发生在真正落库那一刻，所以**模型中途失败时旧审核结果原样保留**，不会留下半成品；
无 `force` 时仍是 409，旧语义不变。

- 三类结果从「全局单例 + 列表底部大面板」改为按 `content_id` 分桶，渲染成卡片**紧随其后的兄弟节点**（`.inline-detail`，
  左侧高亮竖条 + 缩进 + 轻微入场动画），后续卡片被自然下推 —— 不再需要滚到底部找结果。
- 新增 `NextSteps` 引导条，把「看完能干什么」直接摆出来：分析后 → 保存到知识库 / 蒸馏为 Q&A / 查看审核断言 / 生成单篇报告；
  审核后 → 生成单篇报告 / 查看作品分析 / 重新审核；报告后 → 复制 Markdown / 查看作品分析 / 查看审核断言 / 重新生成。

- 报告是否已存在走「每内容只探测一次」的懒加载，不随 2s 轮询重复请求。

## 2026-09-10：轮询闪烁修复 + 首页提速 + 结果多版本管理 + 内容删除

范围：`client/`（Dashboard 为主 + App/样式/新组件）、`server/`（唯一一次 schema 变更：审核批次）。
四个问题一并解决：① 创建表单文字闪回跳动；② 首页加载慢；③ 分析/审核/报告缺版本管理，
误入库风险；④ 内容池无法删除。

### 1. 「创建任务」文字闪回 —— 根因是 loading 语义串台

按钮文案 `{loading ? '创建中…' : '创建任务'}` 里的 `loading` 由 **2 秒后台轮询**驱动
（轮询开始 `setLoading(true)`、结束 `setLoading(false)`），于是文案每 2 秒翻转一次，
叠加 `.btn` 的 `transition: background .12s` 就是肉眼可见的闪回 + 排版抖动。顶栏
「同步中… / 更新 HH:MM:SS」同理。

修复：**拆分 loading 语义**。新增 `submitting` 只由用户发起的创建请求驱动按钮，
轮询改用 `syncing`（不驱动任何按钮文案）；按钮加固定 `min-width: 108px`，
标签切换不再引起宽度变化。

### 2. 首页提速：请求数 43 → 3

三个叠加原因与对应处理：

| 原因 | 处理 |
|---|---|
| `App.tsx` 无条件挂载 `KnowledgeBase`，`.view-shell-hidden{display:none}` 只藏不卸，首屏就跑 `GET /kb/documents?limit=100` | 改为**首次点击才挂载**（`kbVisited`），之后保持挂载保留页内状态 |
| 启动时对**每条内容**发 2 条请求探测分析/报告，20 条 = 40 条 | 新增 `GET /contents/summary` 一次拿全派生计数；版本明细改为**打开面板时按需拉** |
| `/health` 每 2 秒探测一次，而它内部会 **spawn 一次 OpenCLI whoami 子进程** | 后端加 30s TTL 缓存；前端降为分级轮询 |

**分级轮询**（自适应递归 `setTimeout`，按当前数据决定下次间隔）：
`/health` 固定 30s；`/collection-runs` 有 running/queued → 2s，空闲 → 10s；`/contents/summary` 10s。

**状态去重**（`client/src/lib/stable.ts`）：`sameJson` 整批去重 + `keepItemsById` 逐条保引用。
只做整批去重不够——后端每次返回全新对象，一条变则整批变，`React.memo` 依然全量重渲染。
配套 `useCallback` 化回调、卡片 `onView/onToggleFocus` 改稳定签名 `(content, view) => void`。

**`/health` 缓存的诚实性**：响应体带 `checked_at`（真实探测时间）与 `cached: bool`，
陈旧状态对调用方可见，**不伪装成实时**。

### 3. 结果多版本管理

**分析**（后端天然已版本化，补前端）：`Analysis[]` 倒序 + 版本下拉；响应新增 `in_kb`，
已入库的版本在下拉里标 `✓已入库`、入库按钮置灰。

**审核**（本次唯一 schema 变更）：原先 `save_review_batch(replace=True)` 在**同一事务内物理删除**
旧 evidence/decisions/claims 再写新批次，旧审核结果不可恢复。改为**新增批次**：

- `claims` + `batch_id TEXT NOT NULL DEFAULT ''` / `batch_seq INTEGER NOT NULL DEFAULT 1`；
  `contents` + `active_batch_id TEXT`。全部走 `_COLUMN_MIGRATIONS` 幂等 ALTER。
- **旧数据零回填**：`active_batch_id` 为 NULL 时回落为 `batch_seq` 最大的一批；旧行
  `('', 1)` 天然就是「第 1 版」。
- 新增 `GET /review-batches`、`POST /review-batches/{id}/activate`；`GET /claims?batch_id=` 可选。
- **修掉一个正确性 bug**：`human_decide` 原本用 `list_claims(content_id)` 重算内容状态，
  版本化后会把**所有批次混算** → 改为只取该 claim 所属批次；激活批次同样按该批次重算。
  重算复用既有纯函数 `resolve_content_review_status`（未改动）。

**警示**：面板顶部常驻警示条（选中非最新版时显示「正在查看第 N 版，最新为第 M 版」）+
入库/重做走 `ConfirmDialog` 二次确认，文案点名版本号「即将把【第 3 版】保存到知识库」。

**报告**：`ReportService` 不读 claims，只用 `content_repo.get()` 重建 scope —— 报告与审核批次
**无数据耦合**，因此**不需要**给报告加 batch 参数。

### 一、只读副本（云端写保护）

判定规则是**默认拒绝 + 显式读豁免**（`app/auth.py::is_read_request`），不是按 HTTP 方法一刀切：

- 放行 `GET`/`HEAD`/`OPTIONS`，外加白名单 `POST /api/v1/kb/search`、`POST /api/v1/kb/ask`（**POST 但纯读**）
- 其余一律 403，**新增写端点自动被拦**，无需维护黑名单

三个必须知道的设计点：

1. 写请求在**请求层**即 403，因此 `collection_runs.py:30` 的 `asyncio.create_task(collector.execute(...))` 永不触发 —— 后台采集在云端不可能被绕过启动。
2. `POST /api/v1/auth/login` 也 403（**故意**）：云端只读副本不需要管理员 Cookie，只读 Token 是唯一凭证。
3. 只读模式跳过 `init_db()`（快照 schema 已完整，启动不必写库）。但 **`/data` 不能挂只读** —— SQLite WAL 需要写 `-wal`/`-shm`，目录只读会让连接直接失败。

### 二、只读 Token（app 用）

app 带 `X-Datapp-Token` 头访问，**只放行读请求**，写请求仍 401。因此 app 不必持有管理员密码，Token 泄露也只丢读权限。未配置 → 通道整体关闭（绝不退化成「空 Token 放行」）。比较用 `secrets.compare_digest` 防时序侧信道。

### 三、红线门禁（用户拍板：不删数据，只堵门禁）

| 层 | 位置 | 作用 |
|---|---|---|
| C1 入库门禁 | `services/knowledge_base.py::vectorize_content` / `vectorize_analysis` | 源内容非 `approved` → `ReviewGateError` → HTTP **409**（状态冲突，非校验失败）。是**状态判断**不是永久拉黑 —— 补审到 approved 即可正常入库 |
| C2 检索过滤 | `repositories/kb.py::iter_retrievable_chunks`（新） | SQL JOIN 过滤，越线 chunk **物理上命中不到**。`iter_all_chunks` 保持原语义供管理/统计 |
| C3 体检豁免 | `tools/verify_schema.py` + `tools/redline_baseline.json`（新） | 存量越线 → WARN；**新增**越线 → FAIL |

C1 的 `ReviewGateError` 继承 `ValueError`，既有的逐条回执分支照常工作，路由层在 `ValueError→422` 之前单独捕获并映射 409。
doc 级批量入口（`vectorize_document`）目前只产生 `manual` 文档、不构成绕过，但仍加了纵深防御判断。

**C2 排序不变量**：干净数据下 JOIN 过滤零行，与 `iter_all_chunks` 结果集完全一致（同 `rowid` 排序）。既有检索排序断言逐字节不变。

### 四、体检工具漏检修复（本轮发现的真问题）

旧的数据层红线检查只 `JOIN contents`（即只管 `source_type='content'`）、只查 `pending`/`blocked` 两种状态，于是**整整漏掉了 analysis 型文档与 `extracted`/`rejected`/`disputed` 三种状态** —— 真库上把 **8 篇越线报成了 1 篇**。

改为**检索视图的补集**：`有向量的 doc 集合 − iter_retrievable_chunks 集合`。检查与被检查对象共用同一个 `_RETRIEVABLE_PREDICATE`，**谓词改了这里自动跟着改，不可能再脱节**。

存量清单落在 `tools/redline_baseline.json` 而不是硬编码进代码 —— 这些 doc_id 是真库特有的，写死在源码里会让工具在其他库副本上把正常文档误判成「已豁免」。基线文件缺失 → 视为空基线（全部 FAIL），安全默认。

### 九、发布时被体检拦下的一个真实缺陷（空审核批次留下悬空指针）

**现象**：`publish.sh` 在第一步体检中止（exit 1），未见任何显式改动：

```
[FAIL] contents.active_batch_id 不存在于该内容自己的批次: 1 条指向
```

**根因（代码缺陷，非脏数据）**：`services/review.py` 在模型一条断言都抽不出来时走
「归入待人工」分支，传入的是**空列表**：

```python
claims = self._clean_claims(raw, content)
if not claims:
    await self.review_repo.save_review_batch(content_id, [], [], [], ReviewStatus.EXTRACTED)
```

而 `repositories/sqlite.py::save_review_batch` 收尾处**无条件**执行
`UPDATE contents SET review_status=?, active_batch_id=?`。空 claims → 一行都不 INSERT，
却把 `active_batch_id` 指向刚生成的 uuid → **悬空指针**。

**为什么体检抓得很准**：`list_review_batches` 是从 `claims` 表 `GROUP BY batch_id` 聚合的，
空批次**压根列不出来**。于是 `_resolve_active_batch` 返回那个孤儿 id，批次列表里却没有任何
一项的 `batch_id` 等于它 —— 界面表现为「状态是 `extracted`、却没有任何批次处于生效」的自相矛盾。
体检正是拿这个不变量做的断言。

**判据（此前被漏掉的一面）**：既有用例 `test_review_empty_claims_goes_extracted` 只断言了
`review_status=EXTRACTED` / `claim_count=0` / `list_claims=[]`，**恰好没断言 `active_batch_id`** ——
所以缺陷长期存在而测试全绿。修复即补齐这个缺口。

**修复**（`repositories/sqlite.py`，仓库层守住不变量，任何调用方传空列表都不会再产生悬空指针）：

- `claims` 非空 → 更新 `review_status` + `active_batch_id`（原行为）
- `claims` 为空 → 只更新 `review_status`，`active_batch_id` 置 **NULL**，回落规则
  （取 `batch_seq` 最大的一批）对残留历史批次仍然生效

**存量数据处置**：`xhs:6a9015e3000000002a03ca60` 的悬空指针置 NULL。该 id 在 `claims` /
`evidence` / `review_decisions` 三张表里**均无任何行**，`review_status` 保持 `extracted`
（审核结论本身不动）→ **零信息丢失，不删任何数据**。改前已用 `sqlite3.backup()` 备份到
`storage/datapp.db.bak-20260910-202333`。

### 十、人工复核通道的死锁（第二个结构性缺陷）

**现象**：真库里有内容停在 `extracted` 推不动，人工在看板上改判 `supported` 也不生效 —— 状态纹丝不动。

**根因**：`services/review.py::human_decide` 只写 `claim.status`，**不碰 `confidence`**。而
`resolve_content_review_status` 的门槛是 `confidence is None or < REVIEW_MIN_CONFIDENCE(0.6) → EXTRACTED`。
模型给不出置信度时写的是 `None` / `0.0`，人工拍板后置信度**仍是 0.0**，重算又判回 `EXTRACTED` ——
改判等于没改。**人工复核这条通道是结构性失效的**，不是偶发。

**修复**：新增 `HUMAN_CONFIDENCE = 1.0`。人工改判为 `supported`/`contradicted` 时，仅当置信度
`None` 或 `< 0.6` 才补上；**已达标的置信度不覆盖** —— 那是模型给出的判定信息，改判只补人不补数。

**回归测试**：`test_human_decide_lifts_confidence_so_status_can_advance`（模型 `unclear` + `conf=0.0`
→ 人工改判 → `approved` 且 `conf=1.0`）、`test_human_decide_keeps_sufficient_model_confidence`
（模型 `conf=0.9` 不被覆盖）。

**真库一致性检查**：「`contents.review_status` vs 从生效批次重算」**0 条不一致**。

## 2026-09-11：底部 Dock 交互重做 —— MacBook 风 Q 弹放大 + 圆角正方形

### 一、需求

> 「像苹果的 mac book 系统一样，点击到某个功能的时候，图标 duang 的一下放大的动态效果……每个功能入口的边框应该是呈现圆角正方形的，而不要现在这样呈现长方形的。」

两条：**① 点击触发的一次性放大脉冲（duang）；② 入口块是圆角正方形，不是扁矩形。**

### 二、根因：用错了动画 API

原实现用 `animateFloatAsState(targetValue = if (isSelected) 1.30f else 1.0f)`。
这个 API 是**跟随状态**的 —— 它把当前值收敛到目标值然后**停住**：

- 选中后图标**一直**保持 1.30 倍，没有「弹一下再回来」；
- **重复点同一个入口，`targetValue` 没变化 → 一个动画都不跑，零反馈**。

要的是「事件驱动的瞬时脉冲」，必须用 `Animatable` + `snapTo` / `animateTo`：

```kotlin
val pulse = remember { Animatable(0f) }
// 点击回调里：
scope.launch {
    pulse.snapTo(0f)                       // 保证重复点也能从 0 起跳
    pulse.animateTo(0.30f, spring(dampingRatio = 0.30f, stiffness = Spring.StiffnessHigh))       // 冲高
    pulse.animateTo(0f,    spring(dampingRatio = 0.55f, stiffness = Spring.StiffnessMediumLow))  // 过冲回弹归位
}
```

`dampingRatio = 0.30`（强欠阻尼）负责「Q 弹」，回落段用较小 stiffness 拉长余韵。

### 三、扁矩形的根因：尺寸被内边距撑出来的

原写法是 `Modifier.padding(horizontal = 10.dp, vertical = 4.dp)` + `clip(CircleShape)`，
触摸区高度由内容决定、宽度由 padding 决定 —— **宽高比不可控**，自然出扁矩形；
而且 `CircleShape` 套在扁矩形上，圆角半径被拉伸成椭圆弧。

改为**固定尺寸 + 显式圆角**：`.size(58.dp)` + `.clip(RoundedCornerShape(19.dp))`。

**58dp 是量出来的，不是拍的**：内容（图标行高 + 标签行高 + 指示圆点）实测约 50dp，
原先试的 52dp 装不下 —— 溢出的圆点被 `.clip()` 静默切掉（首版截图里圆点消失即此因）。
容器同步从 68dp 抬到 76dp 留出放大余量。

### 四、验证：录屏抽帧 + 像素量化

`screencap` 单帧耗时约 200ms，追不上总长约 0.5s 的脉冲（连拍 16 帧全部落在动画结束之后）。
改用 `screenrecord` 录 5.23s（28 帧，约 5.3fps），点两次**当前已选中**的 tab
（页面不切换，画面唯一变量就是动画本身），抽帧后取内容 tab 的**强调色像素**做包围盒：

| 帧 | 文字宽 | 文字高 | 上边界 |
|---|---|---|---|
| r0014（静止） | 26 | 63 | y=1082 |
| **r0019（峰值）** | **38** | **90** | **y=1062** |
| r0025（归位） | 26 | 66 | y=1080 |

- 峰值 **1.46×**，上跳 20px（约 16dp）；
- 峰值后连续 6 帧单调衰减 `38→36→34→34→32→30→26` —— 是**弹簧过冲回落**，
  不是线性归位（线性会直接掉回 26）；
- 两段完整脉冲分别对应两次点击 → **重复点同一入口同样触发**，符合预期。

方块本体宽高比独立测量：**静止态 宽=78px / 高=78px = 1.000**，精确正方形。

对比图存于 `storage/_dock_duang.png`（上：静止 1.0×；下：点击峰值）。

## 2026-09-11：修复 KB 错误码映射 —— 上游不可达被误报成「未配置」

### 一、缺陷

`server/app/api/routes/knowledge_base.py` 的 `_status()` 只判了向量侧的 Provider 错误：

```python
if isinstance(exc, (EmbeddingNotConfiguredError, ModelNotConfiguredError)):
    return 503
if isinstance(exc, EmbeddingProviderError):   # ← 漏判 ModelProviderError
    return 502
return 503                                    # ← ModelProviderError 掉进这里
```

`ModelProviderError`（LLM 上游超时 / 断连）落进兜底分支，被当成 `503 Service Unavailable`。
但 503 在本项目里的语义是**「没配 key」**（见模块 docstring 与
`EmbeddingNotConfiguredError` / `ModelNotConfiguredError` 的处理），
于是「上游不可达（可重试）」被伪装成「服务端未配置」。

docstring 一直写着「Provider(网络可重试)→502」——**规范写了，实现没跟上**。

### 二、影响范围（含一次真实的误判）

`EmbeddingProviderError` 是**向量侧**异常。KB 里 LLM 的调用路径（`clean()` 清洗、
`distill-qa` 蒸馏、`/kb/ask` 作答）抛的都是 `ModelProviderError` —— 也就是说，
**整个 LLM 侧从来就没走到过 502 那条分支**，全部返回 503。

上一轮实测 `POST /kb/analyses/{id}/distill-qa` 返回 503，据此判断为「服务端缺
`DATAPP_LLM_API_KEY`」——**判断错误**。真实情况是同进程的 `/kb/ask` 返回 200 且带 3 条
citation（key 是配好的），distill 只是超过了读超时（实测 120.7s）。错误码把排障方向
整个带偏了：去查配置，而问题在超时。

其余路由（`review.py` / `reports.py` / `analysis.py`）都正确判了 `ModelProviderError`，
**只有 KB 这一处漏**。

### 三、修复

`_status()` 对称判断两侧；`from app.adapters.llm import` 补上 `ModelProviderError`。
`qa.py` 复用 `knowledge_base._kb_or_error`，一处修复覆盖全部 KB + QA 端点。

### 四、回归测试（先证伪再确认）

新增 2 例：

| 测试 | 层次 | 断言 |

| `test_status_maps_both_provider_errors_to_502` | 单元 | `ModelProviderError→502`、`ModelNotConfiguredError→503` 及向量侧对称项 |
| `test_llm_provider_error_maps_to_502_not_503` | HTTP 端到端 | `/kb/qa/distill` 走 `clean()`→`chat_text()` 抛 Provider 错误 → **502** |

**测试有效性已验证**：临时把 `_status()` 还原成旧实现后跑，两例同时变红，

## 2026-09-11：app 端免账号密码登录 —— 新增移动端设备令牌通道

> **标题中的「第三条」已过时**：只读 Token 通道于同日晚些时候整条删除，设备令牌现在是
> **第二条**（另一条是管理员 Cookie）。本节其余内容（设备令牌的设计、权限矩阵、
> 实测证据）全部有效；只有「三条通道」这个计数与权限矩阵里那两列是当时的快照。
> 现行契约见 [app端对接契约.md](app端对接契约.md) §1.3。

### 一、需求与决策

用户诉求：**app 端不要账号密码，只有 Web 看板看数据才要管理员登录。**

上一轮之所以把 app 从只读 Token 切到管理员 Cookie，理由是「app 要继承的功能里一半是写操作，
只读 Token 一律 401」。所以不能简单退回只读 Token —— 那会把分析 / 审核 / 报告 / 向量化 / 删除全砍掉。

三个决策（用户确认）：

1. **保留写操作**，走 app 专用设备令牌（不是退回只读）
2. **令牌缺失 / 配错 → 回落登录页**，不把 app 变砖（`LoginScreen` 整份保留）
3. app 令牌**排除采集类端点** —— app 本就不继承采集，功能零损失

### 二、三条通道的最终权限矩阵

| 通道 | 请求头 / 凭证 | 读 | 写 | 采集模块 |

## 2026-09-11：OpenCLI 采集链路加固（限速 / 错误分类 / 子进程生命周期 / 脱敏）

在现有适配器上做增量加固，不引入新架构。范围：`server/app/adapters/*`、`server/app/services/{collector,throttle,redact}.py`、
`server/app/config.py`、`server/app/api/routes/collection_runs.py`、`server/.env(.example)`、测试。

### 一、修掉真实缺陷：超时/取消不再留活口

- 原实现 `asyncio.wait_for(proc.communicate(), ...)` 超时后直接 `return`，**没有 kill 子进程** ——
  残留的 node 仍挂在 Browser Bridge 会话上，占着 tab lease，后续采集要么撞车要么被上一次的会话状态干扰。
- 现在：硬超时（`命令超时 + DATAPP_OPENCLI_TIMEOUT_GRACE`，默认 60+30s）触发即 `kill + wait`；
  `asyncio.CancelledError` 同样先收进程再抛出；`terminate_active()` 供取消路径调用。
- 取消语义闭环：`CollectorService.cancel()` 改为 async，只有被取消的正是**当前在跑**的任务才终止在途命令，
  并在命令返回后补一次取消判定 —— 否则命令被杀后的失败会盖掉「任务已取消」，run 落成 failed。

### 二、错误分类补齐（对齐 AGENTS.md：429/403/验证码/300017/300031 立即熔断）

- 新增 `is_risk_signal()`：错误码与文案一起扫，命中即 `RATE_LIMIT` 且不可重试 → 计入熔断。
  平台常把风控藏在文案里（"安全限制" / "访问链接异常" / "请求太频繁"），只判错误码会漏。
- 数字码加词边界：`\b403\b` —— note_id 这类十六进制串里出现 `403` 不会被误判成风控。
- 新增「采集环境不可用」（扩展未连接 / daemon 未运行 / ECONNREFUSED / profile disconnected）→
  `NETWORK` 但**不可重试**：分类与可重试解耦，重试只是再失败一次，得先人工把浏览器拉起来。
- 适配器漂移（页面结构不匹配、`ambiguous_option`）仍是 `PARSE`：不重试也**不熔断** —— 这是改适配器的信号，不是风控。

### 三、限速对齐手册 5–30s

- `DATAPP_RATE_PER_SECOND` 默认 0.5（2s）→ **0.1（10s）**，落在 AGENTS.md 区间内；`.env` 同步。

### 一、表结构优化（SQLite，全部走增量迁移，不动已有数据）

- **`collection_runs.latency_ms`（新增列）**：手册 §4.3 要求「必采集的运行指标」里有耗时，之前没落库。

## 2026-09-11：app 端「删除」= 软隐藏 + web 端「重新同步」

### 一、需求与语义选择

app 端要能「删除」内容，但 app 是**消费端**、web 看板才是**管理端** —— 两条通道共用同一套端点、
同一个库。原来的 `DELETE /api/v1/contents/{id}` 是**物理硬删**（按 FK 逆序清掉断言/证据/分析/
KB 文档/报告引用/封面），设备令牌也能调它。照搬这个语义的话，app 上点一下，web 看板里那条内容
一起消失 —— **管理端失去对数据的掌控**，而这批内容不可重采（OpenCLI 依赖已登录浏览器会话）。

所以把两件事拆开：

| | app 通道（设备令牌 / 只读令牌） | web 通道（管理员 Cookie） |
|---|---|---|
| 已隐藏内容 | **完全不可见**（列表/概览/报告/审核/分析/KB/检索/问答） | 照常可见，带「app 端已隐藏」chip |
| 可执行动作 | 隐藏 | 恢复同步（取消隐藏）、彻底删除（现有硬删） |

`DELETE /api/v1/contents/{id}` 一行未改，硬删语义完整留给 web 的「彻底删除」。

### 二、状态只存一个字段：`contents.app_hidden_at TEXT`

用**时间戳**而不是布尔：`WHERE app_hidden_at IS NULL` 与布尔等价，但额外留下「自何时起被隐藏」，
与项目「报告双格式可审计」「模型输出 ≠ 事实」的存证气质一致。落点四处（缺一不可）：

- `schema.sql` 的 `contents` 建表（新库）
- `app/db.py` 的 `_COLUMN_MIGRATIONS["contents"]`（老库幂等 ALTER，列必须可空）
- `app/domain/models.py` 的 `Content`（`app_hidden_at: str | None = None`）
- `sqlite.py` 的 `_content_from_row`（`d.get()` 兜底写法）

**写路径天然安全，已核实**：`upsert()` 用 `ON CONFLICT DO NOTHING`，重新采集同一条内容不会覆盖
已有行；`update_content()` 的 `UPDATE ... SET` 逐列列名显式，不含新列。所以隐藏状态只能由
`set_app_hidden()` 一个入口改变，不存在旁路。

### 三、通道判定放在中间件，且**必须无条件算一次**

`app/main.py` 的 `admin_gate` 里：

```python
request.state.app_channel = not user and (app_token_ok(request) or readonly_token_ok(request))
```

这行写在 `if not user:` 块**之外**。写进去会让管理员 Cookie 请求永远拿不到该字段 —— 那个块只有
Cookie 校验失败才进入，结果是 **web 看板跟着被一起过滤**。也与 `auth_enabled` 无关：本地关掉认证时，
带了 app 令牌的请求依然按 app 通道收窄。

`auth.app_channel(request)` 用 `getattr(request.state, "app_channel", False)` —— **默认 False = 全量**。
反向默认（默认隐藏）会让 web 静默丢数据，且只在不走中间件的路径上出现，极难排查。

### 四、过滤下推到仓储层：显式参数，默认关

所有仓储方法加 `app_visible_only: bool = False`。默认 False = 既有调用方零改动、web 行为逐字节不变
（全量 398 个既有用例未改一行即全绿，这是这条默认值最硬的证明）。显式参数而非隐式上下文，是为了
留一个**可 grep 的审计面**。

### 五、四个必须记住的坑

1. **三值逻辑**：`cX.app_hidden_at IS NULL` 在 `cX` 整行为 NULL（悬空来源）时求值为 TRUE，看着像
   「放行」。`kb.py` 的两条 JOIN 路径靠**同一 AND 组**里的 `cX.review_status='approved'`（对 NULL
   不成立）兜住 —— **这两个条件绝不能被拆到外层 OR**，拆开就是击穿红线。因此
   `iter_retrievable_chunks()` 刻意**不改形态**，只在既有 AND 组里追加 `AND cX.app_hidden_at IS NULL`；
   而 `_APP_VISIBLE_DOC_WHERE` 走 OR 形式，所以额外加了 `cX.content_id IS NOT NULL` 兜底。
2. **404 而非 403**：403 等于告诉 app「这条内容存在、只是被隐藏了」，那就成了一个**存在性预言机**。
3. **过滤必须在 LIMIT/OFFSET 之前**：`list_reports` 在 app 通道下先过滤再切页，否则 app 拿到 50 条里的
   47 条，前端分页全错。
4. **报告是 any-hidden，不是 all-hidden**：`reporting.py` 把每条内容的 `title` 与 `text[:600]` 逐字
   拼进 prompt，渲染的 markdown 结尾又把整个 payload 以 ```json``` 原样打印 ——「部分隐藏」在这个载体上
   无法表达。所以**任一被引用内容隐藏即整篇隐藏**。

### 六、隐藏不级联，可见性靠继承

派生数据（断言/证据/分析/报告/KB 文档/QA 对）**不单独打标记**，可见性在读取时由源 content 的标记
**继承**（各仓储的 JOIN / EXISTS 过滤）。因此恢复是**原子的**：清掉一个字段，全部派生数据同时回来，
不存在「内容恢复了但它的知识库文档还是查不到」这种半残中间态。

两条容易漏的：

- **QA 对的判定依据必须是 doc 的可见性**：`KbQaPair.source_type` 恒为 `'distilled'`，
  `source_id` 可能是 content_id 也可能是 analysis_id（取决于蒸馏入口），本身有**二义**，不能拿它判。
- **`searcher.find_candidates()` 必须过滤 —— 这条防的是写入污染而非读取泄露**：审核与分析会把候选的
  `title` 与正文前 80 字写进 `evidence.excerpt`，候选 id 还会进 `payload.comparison.baseline_content_ids`。
  不过滤的话，一条已隐藏内容会继续「长进」**可见内容**的派生数据里，而那份派生数据 app 是看得到的。

### 七、检索与问答：一处过滤覆盖两条路径

已核实是单一入口：`POST /kb/search` 与 `POST /kb/ask` 都经 `KbService.search()` →
`kb_repo.iter_retrievable_chunks()`；`qa_agent.KbRetriever.retrieve()` 只是转调，没有第二条检索路径。
所以只改一个函数即可。

问答的 citations **不额外处理**：检索侧过滤后，模型若仍引用被隐藏内容的 chunk，会对不齐检索结果 →
走既有的「无有效引用 → 强制拒答并丢弃模型文本」红线。复用红线比另造一套更安全。

### 八、恢复权只归管理端

`auth.py` 新增动作级排除（按方法 + 路径**后缀**）：

```python
_APP_TOKEN_DENY_DELETE_SUFFIXES = ("/app-hidden",)
```

只挡 `DELETE`。若 app 能自行恢复，用户点一下「删除」再点一下「恢复」就绕过了整套可见性机制，
隐藏形同虚设。隐藏本身（`POST .../app-hidden`）仍然放行 —— 那是 app 的本职功能。

为什么不加进 `_APP_TOKEN_DENY_PREFIXES`：那是**前缀**匹配，而 `/api/v1/contents/` 前缀同时是 app
读详情、读分析、提交审核的入口，关掉整个前缀等于把 app 的功能一起关掉；前缀匹配也天然表达不了
「只排除这个后缀」。

2. **通道在不在**：`adb devices` emulator-5554 online。→ 设备连着。
3. **地址还对不对**：`ipconfig` 当前 IPv4 = **`192.168.0.109`**，
   而 `gradle.properties` 里编进 APK 的是 **`192.168.10.145`**。→ 抓到了。

**DHCP 换了整个网段**（`192.168.10.x` → `192.168.0.x`），app 里写死的地址指向一个已不存在的
主机。关键判据是错误形态：**连一个不存在的主机拿不到 TCP RST**，socket 只会一直等，
okhttp 等不下去只能报「流意外结束」—— **不是 `Connection refused`**。把「连接被静默丢弃」
和「明确拒绝」分清楚，才能一眼指向「目标主机不存在」而非「服务没起来」。

**数据零丢失、服务端零故障**，纯粹是 APK 里那个地址过期了。

### 三、中间翻车：`10.0.2.2` 也不行

第一反应是改成模拟器标准别名 `http://10.0.2.2:8000`，结果换了个错：

```
failed to connect to /10.0.2.2 (port 8000) from /10.0.2.15 (port 53518) after 8000ms
```

**超时，不是拒绝。** 本机有 TUN 代理网卡 `198.18.0.1`，大概率是它或防火墙搅的
（同网段的 ICMP 在模拟器里也是 100% loss，但那是 Windows 默认拦 ICMP，不代表 TCP 不通 ——
**ICMP ≠ TCP**，别拿 ping 当判据）。改回局域网 IP `192.168.0.109` 立刻正常。
这条实测结论写进了 `gradle.properties` 与契约 §1.1，免得下次再把它当稳定选项。

### 四、根本问题：改地址只能重编

改 `gradle.properties` → 重新构建 → 重装，换一次网络就要走一遍。这不可接受，所以本轮落地
**app 内运行时切换地址**。三项决策：候选列表探测（**不做网段扫描**）、保存后清会话重新探测、
编译期默认改中性值 `http://127.0.0.1:8000`。

设计上有四个点值得记：

1. **网络层一行没动**。`DatappApiClient.baseUrl` 本来就是 public `var`，`openConnection`
   每次请求现读 → 改它即时生效。只加了 `connectTimeoutMs` 参数、`health()`、以及
   `normalizeBaseUrl()`。
2. **探针必须用根路径 `/health`**。`/api/v1/health` 会 spawn OpenCLI 子进程做真实登录态
   探测（冷缓存 8.9s、偶发 >30s，没装采集工具时 500），拿它做探针会把「服务好得很、只是
   探针慢」误判成「这个地址不通」。这条在本轮之前已写进 §7，这里复用。
3. **探测并发 + 2.5s 超时**，且**先全部发出去再按候选优先级取第一个成功的**，不用「谁先返回
   用谁」—— 后者结果随网络抖动变化，同一个候选列表两次点出不同地址。串行则最坏 4×2.5s=10s，
   用户点一下就等十秒等于卡死。实测点「自动探测」到出结果 <3s，确认没退化成串行。
4. **登录页必须有入口，这不是可选项**。Cookie 模式下地址若填错，冷启动必然停在登录页，
   而「我的」页要会话建立之后才可达 —— 没有它用户被**锁死在登录页**。两处入口共用同一个
   `BaseUrlDialog`，逻辑只写一遍。

### 五、顺手修掉的两个真 bug

1. **`normalizeBaseUrl` 把 `http://` 啃成了合法地址**。原实现 `raw.trim().trimEnd('/')` ——
   尾斜杠剥离会吃掉 scheme 自己的两道斜杠：`"http://"` → `"http:/"` → 补 scheme 成
   `"http://http:/"`，`URL` 解析出的 host 是 `http`，于是**一个本该判非法的串反而变成「合法」
   地址**。改为以 `"://"` 为界切开、只对后半段剥尾斜杠。单测里 `testHostlessUrlReturnsNull`
   就是钉这个的。
2. **自动探测的候选里漏了「当前生效的地址」**。原候选只有输入框里的值，用户**手滑把地址改坏
   之后**才想起来点自动探测 —— 此时能救命的恰恰是那个正在生效的旧地址，而它不在候选里，
   探测必然全灭。`BaseUrlDialog(current: ...)` 本来就把 current 传进来了，只是没用上，补进去。

另：`SessionStore.clear()` 原先是 `prefs.edit().clear()` 全清，会把设备配置（后端地址）一起
抹掉。改成只 remove 会话键。全项目零调用，所以这是**拆雷不是修 bug**。

### 七、边界（**别把「自动探测」当万能**）

候选表只有 5 项且**不做网段扫描**（已明确排除）。DHCP 若换到别的网段、或全新安装恰好
中性默认不通，**候选里一个都命中不了，只能手填**。这是方案的已知取舍，不是 bug。
代码注释与契约 §1.1 都写明了这一点。
