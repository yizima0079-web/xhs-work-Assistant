# 社交内容采集、可信分析与 RAG 知识库——架构设计手册

版本：v1.0  
状态：采集可行性已实测通过，进入主系统架构设计与开发  
适用范围：小红书等社交平台的图文、视频内容采集、可信度审核、趋势分析、知识库问答

> 本文档由发散设计稿 v0.1 升级而来。采集工具锁定为 OpenCLI（`@jackwener/opencli@1.8.8`），采集主链路（whoami / feed / note / comments / search）已在真实登录态实测通过，验证证据见 `opencil采集可行性验证报告.md`。

## 1. 目标与交付边界

### 1.1 目标

构建一条可追溯的数据链路：

```text
平台内容
  -> OpenCLI 采集适配器
  -> 原始文件与元数据落盘
  -> 内容解析与标准化
  -> 多轮信息源审核
  -> 可信内容库
  -> 爆点/风格/账号人设/趋势分析
  -> 结构化报告
  -> RAG 知识库
  -> Agent 检索问答
```

### 1.2 第一阶段验收目标（已完成）

以下验收目标已通过实测达成（验证证据见 `opencil采集可行性验证报告.md` §11/§12/§13）：

- 项目身份、仓库地址、许可证、运行方式可以确认。
- 能在授权或公开数据范围内采集至少一类内容。
- 图文、视频、作者、发布时间、互动指标等字段的可获得性明确。
- 失败、超时、限速、验证码、登录失效、IP 风控均可观测。
- 不突破平台访问限制，不绕过验证码、登录保护或技术防护。
- 相同内容可去重，可保存原始响应、文件哈希和采集时间。
- 连续测试不会对目标平台造成异常流量。

第一阶段未通过时，不开发仪表盘、RAG 和 Agent，只保留采集 PoC、测试记录和失败原因。

### 1.3 非目标

- 不承诺绕过平台风控、验证码、登录限制。
- 不把模型输出当成事实来源。
- 不把“信息源审核”简化为单次搜索或单次 LLM 判断。
- 不将平台媒体文件默认视为可公开再分发内容。
- 不把本地数据库写死为最终形态。

## 4. 采集 PoC（OpenCLI，已实测）

### 4.0 根据 OpenCLI 官方设计的边界

本项目使用的实际组件是 [`jackwener/opencli`](https://github.com/jackwener/opencli)，包名为 `@jackwener/opencli`。官方架构是：

```text
OpenCLI CLI -> localhost:19825 daemon -> ws://localhost:19825/ext
-> Edge/Chrome OpenCLI Browser Bridge 扩展 -> 隔离浏览器窗口
-> 已登录的小红书页面
```

OpenCLI 不是无头 HTTP 爬虫，也不是数据库或分析系统。它只负责复用用户已登录的浏览器会话、调用小红书适配器并返回结构化结果、退出码和错误状态。任务队列、全局并发限制、任务级限速、原始证据保存、去重、审核、报告、数据库和 RAG 必须在 OpenCLI 外层实现。

### 4.0.1 Profile ID 的正确含义

`3jpz9ujj` 是扩展生成的 Browser Bridge `contextId`，不是 Edge 的 `Profile 3` 目录名。只有 CLI/daemon 已启动且扩展通过本地 WebSocket 连接后，以下命令才能确认它在线：

```powershell
opencli profile list
```

预期结果包含 `3jpz9ujj — connected`。`[opencli] OpenCLI extension initialized` 只表示扩展 Service Worker 初始化，不代表 daemon 已连接，也不代表 CLI 可用。

### 4.0.2 正确启动顺序

```text
Node.js >= 20.18.1 -> npm ci -> npm run build
-> node dist/src/main.js doctor / profile list
-> daemon 监听 localhost:19825
-> Edge 扩展显示 Connected to daemon
-> profile list 确认 contextId
-> xiaohongshu search limit=1
-> 使用搜索返回的完整 xsec_token URL 读取详情
```

源码包已包含 `extension/dist/background.js`；CLI 依赖与 `dist/src/main.js` 均已就绪（`npm ci` 232 包 + `npm run build`）。

### 4.1 PoC 分层

不要让业务系统直接依赖 OpenCLI 的内部 API，定义统一采集适配器：

```python
class CollectorAdapter(Protocol):
    def health_check(self) -> HealthResult: ...
    def collect(self, request: CollectRequest) -> CollectResult: ...
    def get_capabilities(self) -> CapabilityReport: ...
```

核心对象：

```text
CollectRequest
  - platform
  - target_type: url | keyword | account | post
  - target
  - max_items
  - date_range
  - media_policy: metadata_only | download_allowed
  - request_id

CollectResult
  - run_id
  - status: success | partial | blocked | failed
  - items[]
  - metrics
  - errors[]
  - evidence[]
```

### 4.2 采集测试矩阵

PoC 不追求大规模数据，追求每种行为都有证据：

| 用例 | 输入 | 观察指标 | 通过条件 |
|---|---|---|---|
| 单条公开图文 | 公开 URL | 响应、字段、媒体、耗时 | 可解析且可复现 |
| 单条视频 | 公开 URL | 视频元信息、下载策略 | 明确能否只取元数据 |
| 小批量列表 | 低数量限制 | 成功率、重复率、耗时 | 无异常突发请求 |
| 账号内容 | 授权范围内账号 | 分页、截止时间 | 能正确停止 |
| 无效 URL | 随机 URL | 错误分类 | 不崩溃，错误可读 |
| 重复任务 | 相同输入 | 幂等性 | 不重复写入内容 |
| 断点续跑 | 中途停止 | checkpoint | 可恢复，不丢状态 |
| 限速探测 | 保守增量间隔 | 429/403/验证码 | 触发即停止并记录 |
| 登录失效 | 失效会话 | 认证错误 | 不循环重试 |

建议测试顺序：单条公开内容 -> 两三条小批量 -> 失败场景 -> 长时间低频测试。任何出现验证码、封禁、明显风控信号的情况立即停止升压测试。

### 4.3 必采集的运行指标

```text
run_id
request_id
platform
target
started_at / finished_at
status_code
latency_ms
retry_count
items_found / items_saved
bytes_downloaded
rate_limit_signal
auth_state
error_code / error_message
response_hash
tool_version / git_commit
```

> 现状（2026-09-11 核对）：`response_hash` / `auth_state` / `status_code` 是 HTTP 语义，OpenCLI 走的是子进程调用，没有这三个概念 —— 不硬造字段。
> 已落库的是 `run_id`、`platform`、`target`、`started_at` / `finished_at`、`latency_ms`（仓储层用两端时间戳算好落库）、`items_found` / `items_saved`、`retry_count`、`rate_limit_signal`、`error_code` / `error_category`、`tool_version`。
> 字节量按资产粒度记在 `raw_assets.bytes`，不在任务上冗余汇总（汇总口径会随重试/去重变化）。

不要只记录“成功/失败”。需要区分：网络失败、解析失败、平台拒绝、认证失败、内容不存在、触发限速、数据字段缺失。

### 4.4 限速与风控控制器

采集器必须内置以下控制：

- 全局并发上限，默认 1。
- 每平台独立令牌桶或漏桶限速。
- 请求之间加入有上限的随机抖动，但不用于规避平台检测。
- 429、403、验证码、登录异常触发熔断。
- 同一目标的重复请求使用缓存和幂等键。
- 连续失败达到阈值后进入 `blocked`，人工确认后才能恢复。
- 限制单次任务最大条数、最大媒体大小、最大运行时长。
- 任务取消后不再自动重试。

状态机：

```text
queued -> running -> success
             |          |
             |          -> partial
             |
             -> retry_wait -> running
             -> blocked
             -> failed
```

重试只允许用于临时网络错误和明确可恢复的服务错误；认证失败、权限失败、验证码和风控信号禁止盲目重试。

### 4.5 PoC 验收阈值

第一版不设“越多越好”的采集指标，建议采用可解释阈值：

- 单条公开内容解析成功率：至少 90%。
- 关键字段完整率：至少 80%，缺失字段必须被显式标记。
- 重复任务重复写入率：0%。
- 错误分类覆盖率：至少覆盖网络、平台拒绝、认证、解析、内容不存在五类。
- 失败任务可重放率：100%，且不会制造重复记录。
- 所有风控信号可在日志和任务详情中定位。

阈值只用于决定是否进入下一阶段，不代表对平台长期稳定性的承诺。

## 5. 原始数据、标准化与媒体存储

### 5.1 三层数据模型

```text
Raw Layer       原始响应、网页快照、媒体文件、请求日志，不改写
Normalized Layer 标准化内容、作者、指标、文本、媒体引用
Curated Layer   审核通过、带证据链、可分析、可进入知识库的内容
```

原始层必须保留：

- 采集时间、来源 URL、平台、适配器版本、commit。
- 原始响应或脱敏后的原始快照。
- 文件 SHA-256、MIME、字节数、分辨率、时长。
- 解析器版本和解析错误。

### 5.2 内容统一模型

```json
{
  "content_id": "platform:platform_item_id",
  "platform": "xhs",
  "platform_item_id": "...",
  "content_type": "note|video|image|mixed",
  "canonical_url": "...",
  "author_id": "...",
  "author_name": "...",
  "published_at": "...",
  "collected_at": "...",
  "title": "...",
  "text": "...",
  "media": [],
  "engagement": {
    "likes": null,
    "comments": null,
    "shares": null,
    "collects": null
  },
  "raw_refs": [],
  "provenance": {},
  "review_status": "pending"
}
```

互动数据必须带采集时间，因为点赞、评论等指标是快照，不是永久事实。

### 5.3 媒体策略

优先保存元数据和来源引用；只有在权限、用途和平台规则允许时才下载媒体。媒体文件与数据库分离，数据库只保存对象键、哈希和派生信息。图片、视频解析产生的 OCR、ASR、关键帧属于派生数据，必须保留工具版本。

## 6. 多轮信息源审核与可信度体系

### 6.1 审核不是单一分数

将“可信度”拆成可解释维度：

```text
source_quality       来源质量
evidence_completeness 证据完整度
cross_source_agreement 多源一致性
temporal_freshness    时效性
claim_specificity     断言可验证性
model_uncertainty     模型不确定性
```

最终状态不直接由 LLM 决定，而由规则、证据和人工复核共同决定：

```text
unreviewed -> extracted -> claims_built -> cross_checked
                                      -> needs_human_review
                                      -> approved / rejected / disputed
```

### 6.2 断言级审核

一篇内容可能同时包含事实、观点、广告和推测，不能以文章为粒度整体判定。先拆成 Claim：

```json
{
  "claim_id": "...",
  "content_id": "...",
  "text": "某产品在某时间获得某项认证",
  "claim_type": "fact|opinion|prediction|promotion",
  "entities": [],
  "time_scope": "...",
  "evidence_refs": [],
  "verification_status": "unverified|supported|contradicted|unclear",
  "reviewer": "rule|model|human"
}
```

### 6.3 推荐审核流水线

1. 提取标题、正文、字幕、OCR、作者、发布时间和互动快照。
2. 把内容拆成原子断言，区分事实、观点、推测、营销话术。
3. 对关键实体、时间、数字和引用进行搜索或数据库交叉验证。
4. 计算来源等级与证据覆盖率。
5. 对冲突来源保留双方证据，不强行合并。
6. 对高风险主题进入人工复核。
7. 生成审核结论、依据和待复核项。

### 6.4 来源等级示例

| 等级 | 来源 | 用途 |
|---|---|---|
| A | 官方公告、原始论文、监管/标准机构 | 核心事实 |
| B | 主流媒体、专业机构、可追溯行业报告 | 交叉佐证 |
| C | 有明确作者和引用的专业内容 | 背景与观点 |
| D | 普通社交账号、转载、无出处内容 | 线索，不作为唯一证据 |

结论必须标注“事实/推断/观点/未知”。无法核验的内容允许进入线索库，但禁止无标记进入高可信知识库。

## 7. 后端服务设计

### 7.1 服务边界

```text
ingestion-service       采集任务、适配器、限速、原始数据
processing-service      清洗、去重、OCR/ASR、文本标准化
review-service          断言提取、多源检索、审核状态
analytics-service       爆点、风格、人设、趋势、报告
knowledge-service       切分、向量化、索引、引用
agent-service           查询改写、检索、重排、回答
```

初期可以部署在一个 FastAPI 进程中，但代码边界按服务拆分；异步任务统一走队列，避免 HTTP 请求阻塞。

### 7.2 核心 API

```text
POST   /api/v1/collection-runs                 创建采集任务
GET    /api/v1/collection-runs/{id}             查看进度与错误
POST   /api/v1/collection-runs/{id}/cancel      取消任务
GET    /api/v1/contents                         内容列表
GET    /api/v1/contents/{id}                    内容详情与证据
POST   /api/v1/contents/{id}/review             提交审核
POST   /api/v1/analyses                        创建分析任务
GET    /api/v1/reports/{id}                     获取结构化报告
POST   /api/v1/knowledge/index                  建立知识库索引
POST   /api/v1/agent/query                      知识库问答
GET    /api/v1/metrics/overview                 看板指标
```

所有异步接口返回 `job_id`；前端通过轮询或 SSE 获取进度。API 响应统一包含 `request_id`，便于定位跨服务问题。

### 7.2.1 实际接口与手册的差异（2026-09-11 核对）

实现里多出来、手册未列的接口：`auth/*`（会话登录）、`browser/*`（Browser Bridge 状态/连接/重试）、`collection-requests`（app 申请单，见 §8.1）、`kb/qa/*`（Q&A 蒸馏与人工审核）、`contents/summary`、`review-batches`、`claims/{id}/decision`、`kb/documents/delete`。

手册写了、但实现走的是另一条路径的三个：

| 手册 | 实际 |
|---|---|
| `POST /analyses` | `POST /contents/{content_id}/analyze` + `GET /analyses/{analysis_id}` |
| `POST /knowledge/index` | `POST /kb/documents/vectorize`（单篇） / `POST /kb/documents/{id}/vectorize` |
| `POST /agent/query` | `POST /kb/ask` |

**未实现**：`GET /api/v1/metrics/overview`。看板指标当前由前端聚合 `health` / `collection-runs` / `contents` 三个接口得到 —— 本地单用户量级下这样更简单，等出现第二个消费方（比如第三方系统要出报表）再抽服务端聚合接口。

另外上面那句「API 响应统一包含 `request_id`」目前也**没有实现**：`request_id` 只作为`collection_runs` 的业务字段（关联 app 申请单）存在，响应体里不带。

## 8. 数据库设计

核心表：

```text
collection_runs       采集任务
collection_events     采集事件与错误
raw_assets            原始响应和媒体对象
contents              标准化内容
authors               作者快照
engagement_snapshots  互动指标快照
claims                原子断言
evidence              证据与来源
review_decisions      审核决策
analyses              分析任务与结论
reports               报告正文与版本
knowledge_documents   知识库文档
knowledge_chunks      文档切片
knowledge_embeddings  向量引用
agent_sessions        Agent 会话
audit_logs            用户、任务、状态变更审计
```

关键约束：

- `contents(platform, platform_item_id)` 唯一。
- 原始媒体使用内容哈希去重。
- 审核结果不可覆盖历史，只能追加新版本。
- 报告保留输入内容 ID、分析版本、模型版本和生成时间。
- 知识库切片必须反向引用原始内容和证据。

### 8.1 实际实现与手册的差异（2026-09-11 核对）

真库与 `server/schema.sql` 共 13 张表，由 `server/tools/verify_schema.py` 逐表逐列比对：

```text
collection_runs        采集任务（含 latency_ms / rate_limit_signal / tool_version）
collection_events      采集事件与错误分类
collection_requests    app 提出的待放行采集申请（手册未列，见 7.2.1）
raw_assets             原始响应与媒体资产（mime / sha256 / bytes / storage_path）
contents               标准化内容（UNIQUE(platform, platform_item_id) 去重）
claims                 原子断言（batch_id / batch_seq 做审核版本化）
evidence               证据与来源
review_decisions       审核决策（含 reviewer / 时间）
analyses               单条内容分析（JSON + Markdown）
reports                报告（JSON payload + Markdown）
kb_documents           知识库文档（content_hash 幂等去重）
kb_chunks              切分后的片段 + 向量（embedding 存 JSON）
kb_qa_pairs            Q&A 知识对（draft / approved / rejected）
```

与手册表清单的差异，以及为什么：

| 手册写的 | 实际 | 说明 |
|---|---|---|
| `authors` | 不建表 | 作者是随内容一起取回的快照字段，落在 `contents.author_id` / `author_name`；目前没有第二个消费方 |
| `engagement_snapshots` | 不建表 | 互动是采集时刻的快照，落在 `contents.engagement`(JSON)。要画「互动随时间变化」时再拆表，现在拆等于给每条内容预置一张空表 |
| `knowledge_documents` / `knowledge_chunks` / `knowledge_embeddings` | `kb_documents` / `kb_chunks` | 表名缩短；向量直接存 `kb_chunks.embedding`(JSON)，单机量级下没有独立向量表的必要 |
| `agent_sessions` | 不建表 | 问答是无状态单轮（问题 → 检索 → 引用），没有会话概念 |
| `audit_logs` | 不建表 | 采集侧审计走 `collection_events`，审核侧走 `review_decisions`（带 reviewer 与时间）。两条线各有归属，再建一张通用审计表只会变成没人查的垃圾桶 |
| —— | `collection_requests` | 手册没写但必须有：app 端**只能提交申请**，放行由 web 管理端做。设备令牌会被编译进 APK、可被反编译，用它直接触发真实平台采集是不可接受的 |

索引（全部由 `schema.sql` 与 `app/db.py` 的迁移脚本落库）：

| 索引 | 覆盖的查询 |
|---|---|
| `contents(platform, platform_item_id)` UNIQUE | 幂等去重、按平台取内容 |
| `idx_contents_review_status` | 看板按审核状态筛选与计数（最常用维度） |
| `idx_claims_content_batch(content_id, batch_id, batch_seq)` | 取某内容的批次、按 (content_id, batch_id) 取行、`MAX(batch_seq)` —— 一个复合索引覆盖三种形态，取代原先 `idx_claims_content` + `idx_claims_batch` 两个窄索引 |
| `idx_evidence_claim` | 断言 → 证据 |
| `idx_decisions_claim(claim_id, created_at)` | 断言 → 审核历史 |
| `idx_analyses_content(content_id, created_at)` | 内容 → 分析列表（按时间） |
| `idx_kb_doc_source(source_type, source_id)` | 来源 → 知识库文档（列表页「已入库」标记） |
| `idx_kb_doc_hash` | `content_hash` 幂等去重 |
| `idx_kb_chunks_doc(doc_id, chunk_index)` | 文档 → 片段（有序） |
| `idx_kb_qa_doc` / `idx_kb_qa_status` | 文档 → Q&A 对；按状态分页 |
| `idx_coll_req_status(status, created_at)` | 待放行申请单 |
| `idx_events_run` / `idx_assets_run` | 任务 → 事件时间线 / 原始资产 |

**刻意不做的事**（避免为了「看起来完备」引入负担）：

- 不加重建式约束（CHECK、补挂表级外键）：SQLite 改约束要整表重建，而真库里已有真实数据。枚举合法性由 `verify_schema.py` 的 `ENUMS` 体检 + 应用层枚举类（`domain/enums.py`）双向保证，比一次高风险迁移划算。
- 不给 `reports.content_ids`(JSON) 建关联表：按内容查报告目前是 `content_ids LIKE '%"id"%'` 取余量 + `json.loads` 精确判定（`repositories/sqlite.py`），单机量级下就是几百行扫描。报告上到万级再拆 `report_contents(report_id, content_id)`。
- 不给 `raw_assets.sha256` 建索引：手册要求「媒体按内容哈希去重」，但当前只有写入没有按哈希回查 —— 没有真实查询就不建索引。

迁移机制（`app/db.py`）—— `CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，所以：

- `_COLUMN_MIGRATIONS`：差量 `ALTER TABLE ADD COLUMN`，如 `collection_runs.latency_ms`、`contents.app_hidden_at`；
- `_POST_MIGRATION_DDL`：补列**之后**才建得出来的索引，以及显式 `DROP INDEX` 掉被新索引取代的窄索引；
- `_DEFAULT_DRIFT_REPAIRS`：**列默认值**漂移。`ADD COLUMN` 改不了已有列的默认值，`CREATE TABLE IF NOT EXISTS`
  也不会更新它，只能整表重建（建影子表 → 拷同名列 → 换名 → 补回索引，`_rebuild_table`）。
  只在真库默认值与 `schema.sql` 不一致时触发，正常库零开销。目前唯一一条是 `kb_documents.status`。

两条路径（全新库走 `schema.sql`、老库走迁移）都必须独立跑通 —— 这正是建在迁移列上的索引不能写进 `schema.sql` 的原因：老库 executescript 阶段还没有那两列，会直接报 `no such column`。

## 9. 报告输出规范

报告采用“机器可校验 JSON + 面向人的 Markdown”双格式。先生成 JSON，再渲染 Markdown，避免只生成不可审计的自然语言。

### 9.1 报告结构

```json
{
  "report_id": "...",
  "scope": {
    "platforms": ["xhs"],
    "content_ids": [],
    "time_range": {}
  },
  "executive_summary": "...",
  "viral_patterns": [
    {
      "pattern": "...",
      "evidence_content_ids": [],
      "confidence": 0.0,
      "counterexamples": []
    }
  ],
  "presentation_style": {
    "visual": [],
    "text": [],
    "video": [],
    "interaction": []
  },
  "account_persona": {
    "hypotheses": [],
    "evidence": [],
    "confidence": 0.0
  },
  "trend_direction": {
    "topics": [],
    "direction": "rising|stable|falling|uncertain",
    "window": "..."
  },
  "limitations": [],
  "source_refs": [],
  "analysis_version": "..."
}
```

### 9.2 分析原则

- “爆点”必须来自内容样本和指标，不允许只根据模型直觉下结论。
- “人设/IP”只能称为分析假设，必须给出支持证据和反例。
- “趋势”需要时间窗口、样本量和基线；没有足够样本时输出“不确定”。
- 播放量、点赞量等平台指标不等价于内容质量。
- 跨平台比较必须做平台指标口径说明。

## 10. RAG 知识库与 Agent

### 10.1 入库门槛

推荐分层入库：

```text
verified      审核通过，可作为回答依据
provisional   证据不足，可检索但回答必须标注不确定
lead           仅作为线索，不直接支撑结论
rejected       不进入默认检索
```

默认 Agent 只检索 `verified` 和满足条件的 `provisional`，禁止把 `lead` 混入无标记答案。

### 10.2 切分与索引

- 按标题、段落、字幕时间片、评论主题和证据段落切分。
- 保留 `content_id`、`claim_id`、来源 URL、时间范围、审核状态。
- 同时建立关键词索引和向量索引，采用混合检索。
- 先召回，再按来源等级、审核状态、时间新鲜度、语义相关性重排。
- 结果不足时明确输出“知识库没有足够证据”，不让模型补全。

### 10.3 Agent 问答链路

```text
用户问题
  -> 意图识别/查询改写
  -> 权限与范围过滤
  -> 混合召回
  -> 证据重排
  -> 上下文压缩
  -> 模型生成
  -> 引用校验
  -> 输出答案与证据链接
```

Agent 输出至少包含：结论、证据引用、时间范围、可信状态、无法确定的部分。模型不得生成知识库中不存在的具体数字、出处或平台行为。

### 10.4 RAG 评估集

建立固定问题集，覆盖：

- 直接事实问答。
- 跨内容对比。
- 趋势总结。
- 来源冲突。
- 知识库无答案。
- 时间范围过滤。
- 低可信内容误导。

指标：召回率、引用命中率、引用正确率、无答案识别率、幻觉率、回答延迟。

## 11. 前端数据看板

首屏建议分为四块：

```text
采集健康度：任务成功率、限速事件、待处理队列
内容概览：平台/类型/时间/作者分布
分析洞察：爆点、风格、主题、趋势
可信与证据：审核状态、冲突断言、待人工复核
```

必须支持从图表下钻到内容详情，再下钻到原始数据和证据；所有图表显示数据时间范围、样本数和更新时间。

## 12. 安全、合规与数据治理

- 只采集公开或用户明确授权的数据。
- 凭证、Cookie、Token、Authorization 和签名参数只通过安全配置或受控凭证存储注入，不写入代码、日志、报告或普通导出。含 `xsec_token` 的来源 URL 必须脱敏保存。
- 原始内容和媒体访问按用户、项目、平台授权控制。
- 日志对个人信息、Cookie、Authorization、手机号等字段脱敏。
- 提供数据删除、导出和保留期限配置。
- 记录采集目的、来源、时间和处理版本。
- 不存储超出业务需要的个人信息。
- 对媒体和全文设置访问权限及过期策略。
- Agent 回答带来源，不把第三方平台内容重新包装成无来源原创事实。

## 13. 观测与故障处理

### 13.1 统一可观测性

每个请求、任务和派生对象携带：

```text
request_id
trace_id
run_id
content_id
adapter_version
parser_version
model_version
```

> 现状（2026-09-11 核对）：真正贯通全链路的只有 `run_id` / `content_id`；`tool_version`（`opencli@<version>`）已随采集任务落库。
> `trace_id` / `parser_version` / `model_version` / `adapter_version` **尚未实现** —— 当前是单进程单用户本地部署，没有跨服务调用链，加 trace 只是空壳。
> 等 M5 云化拆服务时按真实调用链补，不为「凑齐字段」提前埋点；`adapter_version` 的部分语义已由 `tool_version` 覆盖。

监控指标：任务成功率、字段完整率、去重率、审核通过率、证据覆盖率、报告生成延迟、RAG 引用命中率、Agent 无答案率、队列积压、存储增长量。

### 13.2 失败处理

失败任务必须保留输入、状态、错误分类和最后一次响应摘要。修复后通过原 `run_id` 重放，禁止手工直接改库伪造成功。
